# Other text an agent reads: clear, minimal, checkable, at the right altitude

Judge this text by how it reaches the agent. If a program or hook puts it in
context in a way the path does not show, judge it as that carrier and apply its
practices. Then ask: does each line earn its place, leading with the action? Is
it pitched as a rule the agent can apply, neither a keystroke script nor a
platitude? Does each step end in evidence the agent can show? Does a rule that
must always hold have a mechanism, not louder words?

## How it loads decides what it costs
- A page the agent opens when a rule names it costs nothing until then. Keep it that way: point to it by path, and do not import or paste it into an always-loaded file.
- Text a program prints into context, such as a command's prompt or a monitor's message, is a carrier too. If it prints every session or on every tick, treat it as always-loaded: short, quiet when nothing needs doing, and pointing to a command for depth.
- A subagent sees only its brief and the files it loads. A step that hands work over puts everything needed in the brief. (Claude Code)
- After compaction, only the start of a long loaded body may survive. Put the instructions that hold throughout at the top. (Claude Code)

## Altitude and length
- Too low is a brittle list of exact commands that breaks when the setting differs. Too high is advice with no concrete signal. Aim for a rule and a discriminator the agent can apply to a case nobody foresaw.
- Current models need less: a brief instruction steers most behaviour. Text written for older models is often too prescriptive. (both)
- Minimal is not short. Keep what the agent needs to act; move the long why into the reference page the steps point to.

## Clarity
- Open with the action and its result; history can wait. Use numbered steps where order matters.
- Apply the colleague test: could a capable reader with only this text open carry it out?
- Use plain wording. Say what each "never" covers and why, so the agent can see when a case falls outside it. Stacked emphasis causes over-application.
- One canonical example teaches the pattern; a catalogue of variants teaches that everything is a special case.

## Verification
- End each step with a done-signal: a path that exists, a URL, an exit status, output to paste back. An instruction without one is easy to skip.
- Request proof and a brief summary, not a transcript of reasoning.
- Only a separate check confirms a claim, such as a fresh-context reviewer or a test run before and after, not by its author's account.

## Mechanism
- Text is weighed, not obeyed. A rule that must fire every time needs a hook, a permission denial or a build that fails without it. Another model's verdict informs a person; it does not gate the work.
- Corrected twice on the same rule, change the mechanism, not the sentence.
