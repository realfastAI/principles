Nothing keeps a project's principles held between audits: `principles` reports a changed member, but nothing in the
project's guidance tells an agent to act on that report, so the drift waits until someone thinks to audit. This
command shows the map of `sticking-to-your-principles`, the principle that does that keeping, with its description and
an activation for all work. Run it to set principles up, once a first principle is mapped and audited. It writes
nothing: no map, and none of the project's guidance. While `already_mapped` is false, `map_file` and `map` are the map the printed `add-member`
creates, with the passage as its first member, so no map without members waits while the passage waits to be placed.

The first member need not be the passage. Any file or setting in the project that keeps the principles in front of
the agent can be, such as a timer of the project's own, or the committed setting that enables the plugin for the team,
its `enabledPlugins` line. This helps teammates only if they can install the plugin from a marketplace they can
access. Map it with the other `add-member` the question prints, whose role names the step it runs
and what starts it, a hook, a timer or a reader. A completed full audit's `next_action` offers this
command until the map has a member, of any kind. A mapped member says only that the project names
something to keep the principles held; this principle's audit judges whether it does. An owner who enables the
plugin only at user scope has nothing in the project to map: the question says so, and names the two ways on, to
commit the project-scope enablement and map its line, or to leave principles not set up for now.

It proposes one short passage, the same for any entry file every session loads, worded for a reader who may not
have `principles` installed, and reports, under `entry_files`, whether `CLAUDE.md` and `AGENTS.md` exist and, as
`links_to` and `by`, whether one links the other by a symbolic link or an import line. In git, `tracked` is false on
an entry file git does not hold, being untracked or ignored, or that links to one it does not hold: it may be kept
out of git on purpose, as its owner's own, so ask them before you place the passage there. An entry file whose text
cannot be read names why under `not_read`, such as `invalid_encoding`; a missing `links_to` beside it does not mean
it has no import, since its text was not read. `passage` gives the passage's text with its `bytes` and
`estimated_tokens`, since it loads in every session, and `presumes` says what it asks of a teammate without
`principles`. `runs_from` says whether this run came from the Claude Code plugin or from the command line, and
`session_start_hook_in_this_session` whether the plugin's session-start hook, which reports changed members, runs
in the session this run is part of. While it does not, `hook_setup` names `show-hook-setup`, which prints the hook
entries that report changed members without the plugin. Neither says anything of a teammate's sessions, which this
tool cannot see, so
weigh with the user who the passage serves.

Run again before the passage is mapped, it proposes the same again. Where the map is already there, it shows the map
as the project holds it, with `already_mapped` true. `members_in_entry_files` names the map's members already in
`CLAUDE.md` or `AGENTS.md`. Once the map has a member, the question no longer asks to place the passage: it lists
each member's place and role, and asks, with the user, which step each lacks of running
`principles list-member-problems --short` at session start, after a compaction and after each commit that edits a
mapped file, offering the passage, with its size, as one way to add one.

With no member mapped, show the user the passage, agree where it goes, and write it there yourself; then map it with the printed
`add-member`, giving `--section` the heading you placed it under. Where a passage the project already has carries
one of its steps, leave the step out and map that passage too, with the other `add-member` the question prints.
Where only a reader enforces a step, say so in what you place. Link to where the project says how a teammate gets
`principles`; where it says nowhere, tell the user that a teammate reading the passage cannot act on it. The
passage's member carries no check, since a command stored in the map runs on every teammate's machine, where
`principles` may not be installed.

`existing_principles` lists the project's other principles as `list-principles` does. While there are none,
`next_action` leads to `list-candidate-files` to map the first, since this principle's first full audit has nothing
to keep held yet. Once there are, it leads to that audit. In git, committing the map and the entry file is the
passage member's baseline; outside git, that first full audit gives it one.

Example:

    %{executable} show-meta-principle-passage
